# facts about rcc and robo framework

Create an environemtn: 

- go to the fodler wiht the yaml files 
- Create env with "name" & acitvate: `rcc task shell --space name`
- Just create the env: `rcc holotree vars --space name`

Run a command in the env "name": 

`rcc task script --space name --robot <path to robot.yaml> -- robot <path to suite.robot>`


# Ideas


- each folder (example/templates) shoudl be self-contained, meaning that it should contain all the files needed to run the tests, including the robot.yaml and conda.yaml files. This would make it easier for users to understand how to set up their own tests, as they can simply look at the examples and templates to see how everything is structured. Also copying the files would be easier, as they are all in one place.
- Github actions should run all rf tests automatically on evr ypush, including bulding all the eivonrments to make sure that they really work on the user side. 
- The templates section coudl contain scaffolding templates for different types of tests, e.g. API tests, UI tests, web tests etc. This would make it easier for users to get started with Robotmk and Robot framework, as they can simply copy and modify the templates to fit their needs.
- A VS code extension (to be done) could access the templates in this repo and provide a quick way to scaffold new projects directly from the editor. This would further lower the barrier to entry for users who want to get started with Robotmk and Robot framework.
- if there are for exmaple multiple  web tests with the same dependencies, the conda.yaml fiel in each folder looks the same. I used to have a wrape script around rcc which read the current fodler name and creates a env space with the fodler name. However, even in that case, rcc will copy a lot of files. There should be a hidden folder with a file holding the space name to use. In that case the same space can be used for all templates/examples which have the same conda.yaml file. 
- A auto genrated table of contents in the readme which gives an overview about all the examples and templates in the repo, including a short description and a link to the folder. This would make it easier for users to find the example or template they are looking for, and also give them a quick overview of what is available in the repo.
- A section in the readme with best practices for writing Robotmk tests, including tips for maintaining and debugging tests, as well as common pitfalls to avoid. This would help users write better tests and maintain them more easily over time.
- A section in the readme with a link to the RCC torubleshooting guide in the robotmk blog. 
- the test and templates usable by the user (each containing the robot.yaml and conda.yaml files) should be artifacts generated by copier. This would make it easier to maintain the examples and templates, as they can be generated from a single source of truth, and also make it easier to update the examples and templates when there are changes to the underlying structure or dependencies. For example, when I want to update a versin number for browser library in the conda.yaml file, I can simply update it in the copier template, and then regenerate all the examples and templates with a single command. This would save a lot of time and effort, and also ensure that all the examples and templates are always up to date with the latest changes because they are generated from the same source of truth and tested afterwards with the Github actions.
- The Github actions should be testable also locally on my machine. 
- The tests should use their own binary of rcc, to download from https://github.com/elabit/robotmk/releases/download/v4.0.0/rcc_linux64, to save in a local hiden flder inside the repo and to use for all rcc actions. This would ensure that the tests are always using the same version of rcc, and also make it easier to update the version of rcc when needed, as I can simply update the binary in the hidden folder and all the tests will use the new version without any change needed in the test code. This would also make it easier to test the Github actions locally, as I can simply use the same binary for local testing as well.
- I want to use the "release please" Github action to automate the release process for this repo. 
- the system should be able to also test multiple combinations of dependencies, for example Robot Frameork 6 and 7, and Browser Library 19.1 and 19.2. This would ensure that the examples and templates are compatible with different versions of Robot Framework and Browser Library, and also make it easier for users to choose the version they want to use for their tests. The Github actions could be configured to run the tests with different combinations of dependencies, and report any issues or incompatibilities that arise. This would help ensure that the examples and templates are always up to date and compatible with the latest versions of Robot Framework and Browser Library. The tests shoudl always only run for the versions which have changed. 
- The main brahch should always contain a wokring version of the examples and templates, which use the latest versions of the dependencies. This would ensure that users can always rely on the examples and templates in the main branch to work correctly. For older versions and their combinations, there could be separate branches or tags that users can access if they need to use specific versions of the dependencies. This would help ensure that users have access to working examples and templates for the versions they need, while also keeping the main branch up to date with the latest versions of the dependencies.
- All templates and eamples shoudl also be runnable in a github codespace. If RCC is possible, use that. We should avoid to clutter the artifact folders fo rht user more iwht files he does not need iwht his work with Robotmk. For example, we shoudl avoid that there are files like pyproject.toml or setup.py in the examples and templates, which are not needed for the user to run the tests, but are only needed for the coddespaces. For that, we coudl have another artifact fdler jsut for the codespaces, which contains all the files needed for the codespaces to work, but is not included in the examples and templates folders. This would help keep the examples and templates folders clean and focused on the user needs, while still providing all the necessary files for the codespaces to work correctly. The Github actions could also be configured to test the examples and templates in a codespace environment, to ensure that they work correctly in that environment as well.
- For web tests, codespaces should use a devcontainer which also has a VNC desktop. Example: https://github.com/manykarim/ai-workshop-rbcn-2026/tree/main/.devcontainer (omit the AI stuff). This would allow users to run the web tests in a codespace environment with a VNC desktop, which can be useful for debugging and maintaining the tests.
